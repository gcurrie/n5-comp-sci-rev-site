Introduction

Evaluation is the final phase of the development process: stepping back from the finished program and judging it honestly. Not "does it run?" — you settled that in testing — but is it actually any good? At National 5 that judgement is made against four criteria, and each one gets its own section below, with a worked example of the kind of evaluation statement that earns marks.

Key Terms

Fitness for purpose
Does the program do everything the functional requirements said it must?
Efficient use of coding constructs
Does the code avoid unnecessary repetition and wasted checks — using loops and elif chains where it should?
Robustness
Does the program cope with exceptional data without crashing?
Readability
How easy the code is for a human to read — commentary, meaningful identifiers, indentation and white space.
ℹ️
What the exam expects: you should be able to describe, identify and exemplify the evaluation of a solution against all four criteria — and in the assignment, you'll write a short evaluation of your own program.

Fitness for Purpose

A program is fit for purpose if it does what it was supposed to do. And "supposed to" isn't a vibe — it's the functional requirements agreed way back in analysis. Meet them all: fit for purpose. Miss any: not fit for purpose, no matter how nice the code looks.

Worked example — evaluating fitness for purpose

The requirements said: accept a percentage mark between 0 and 100, and display the matching grade. The finished program displays grades correctly, but accepts a mark of 400 without complaint.

Evaluation statement: "The program is not fully fit for purpose. It displays the correct grade for valid marks, but it was only supposed to accept percentages between 0 and 100 — it currently accepts values outside this range."

Notice the shape: a clear judgement, backed by a specific requirement. Compare a fit-for-purpose statement: "The program is fit for purpose, because it asks for the user's age and displays an error if a negative number is entered — meeting all the stated requirements."

⚠️
Don't be too kind! If it isn't fit for purpose, say so. Vague, generous statements ("it mostly works fine") lose marks — always tie your judgement to the specific requirements.

Efficient Use of Coding Constructs

Efficient code gets the job done without unnecessary repetition or wasted checks. The SQA loves showing you an inefficient program and asking how to improve it — and the answer is almost always one of two constructs you already know.

Repeated code? Use a loop

Worked example — from repetition to a loop
Python — inefficient
print("Hello!")
print("Hello!")
print("Hello!")
print("Hello!")
print("Hello!")
Python — efficient
for counter in range(5):
    print("Hello!")

Evaluation statement: "The program does not make efficient use of coding constructs — the same print statement is repeated five times. A fixed loop would achieve the same output with less code, and changing the message would only need one edit."

Separate ifs? Use elif (or a nested if)

Worked example — from separate ifs to a chain
Python — inefficient: every condition is always checked
if age == 15:
    year = "S4"
if age == 16:
    year = "S5"
if age == 17:
    year = "S6"
Python — efficient: checking stops at the first match
if age == 15:
    year = "S4"
elif age == 16:
    year = "S5"
else:
    year = "S6"

With three separate ifs, a 15-year-old is checked against all three conditions even though the first one matched. The elif chain stops as soon as it finds the answer — same result, fewer checks. The same logic applies to nested ifs: because the inner if is only reached when the outer condition is true, no impossible combinations ever get checked.

Robustness

A robust program doesn't crash when the user enters exceptional data. Users will type "five" when you asked for 5, press Enter on an empty box, and claim to be -7 years old — a robust program shrugs, shows an error message, and asks again.

How do you evaluate it? With your exceptional test data. Feed the program rubbish and watch what happens: a crash means not robust; a polite error message and a second chance means robust.

Worked example — evaluating robustness

During testing, entering an age of -7 made the program crash with an execution error.

Evaluation statement: "The program is not robust, because entering the exceptional value -7 caused it to crash. Adding input validation — a conditional loop that rejects ages outside the valid range and asks again — would make the program robust."

💡
Spot the connection: input validation isn't just a standard algorithm to memorise — it's the tool that makes programs robust. Exam questions link the two constantly.

Readability

Readability is about making your code easy for a human to understand — you in six months, another programmer, or the person marking your assignment. The computer couldn't care less what your variables are called; the humans reading your code care a lot. There are four techniques, and you're expected to use all of them:

Internal commentary
Comments (lines starting #) explaining what the code does.
Meaningful identifiers
Names that say what they store — age and password, not x and k.
Indentation
Code inside ifs and loops is tabbed in, making the structure visible at a glance.
White space
Blank lines between sections, grouping related code instead of jamming it together.
Worked example — all four techniques in one program
Python
# Ask the user to enter their username, reject if not valid
username = input("Please enter your username: ")

if username == "admin":
    print("Welcome, admin. What would you like to do?")
else:
    print("Access denied, go away...")
  • Internal commentary — the # line explains the program's job.
  • Meaningful identifier — username says exactly what it stores.
  • Indentation — the print statements are tabbed inside their if/else branches.
  • White space — a blank line separates the input from the decision.

Evaluation statement: "The program is readable because it uses internal commentary to explain its purpose, a meaningful identifier (username), consistent indentation inside the selection, and white space to separate the input from the processing."

💡
One nuance for indentation: in Python it's actually required — the program won't run without it. So the readability point isn't just "indent" but indent consistently, so the structure of ifs and loops is obvious at a glance.
